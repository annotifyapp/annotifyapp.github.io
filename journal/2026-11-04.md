**Yarn is a JavaScript package manager** (the main alternative to npm). It ***installs and manages Node.js dependencies*** for a project.

There are two major lines:
- **Yarn Classic (1.x)** — the original, still widely used on older projects, but essentially in maintenance mode.
- **Yarn Berry (2+ / current 4.x)** — the modern rewrite. It is faster, has better monorepo/workspace support, supports Plug’n’Play (optional, no `node_modules`), and is actively maintained. **Yarn 4.18** is the current stable release in that line.

### Why it shows up for your mdBook site on Cloudflare

This notebook uses mdBook, *which itself is worthy of many other questions* ... mdBook itself is pure Rust. On GitHub Pages you can typically just run `mdbook build` and serve the static `book/` output with no Node involvement at all. That is why it “just worked.”

Cloudflare Pages / Workers Builds are more general-purpose CI environments. If the repository contains a `package.json` (and usually a `yarn.lock`), the build system automatically detects Yarn and uses it. Many mdBook setups end up with some Node involvement for:
- Custom themes or extra frontend assets
- Wrangler (if you are deploying as Workers + static assets)
- Build scripts, plugins, or search enhancements

When that happens, Cloudflare uses the Yarn version that is preinstalled in its build image.

**As of mid-October 2026, Workers Builds defaults to Yarn 4.18.1** (updated from 4.9.1). Pages has a similar default (or lets you set it). That is why you had to update to 4.18 for the Cloudflare publish path.

### Why that specific version is critical (and not just extra risk)

1. **Environment matching**  
   Cloudflare’s build image ships with 4.18.x as the default Yarn. Your local installs and the CI installs need to interpret the lockfile the same way. A mismatch in Yarn version is a classic source of “works on my machine / GitHub Pages, fails on Cloudflare” problems.

2. **How you pin or control it**  
   You can force the version with:
   - `"packageManager": "yarn@4.18.1"` in `package.json` (the preferred modern way, via Corepack)
   - The `YARN_VERSION` environment variable in the Cloudflare build settings

   Aligning to 4.18 means you are using the version the platform already has ready instead of fighting it.

3. **Security and maintenance**  
   Recent Yarn 4.x releases include practical improvements (including a default minimum-age gate on newly published packages that reduces supply-chain risk). Yarn 1 is legacy. Staying on an old version while the platform has moved on adds friction and risk, not less.

4. **You can avoid Yarn entirely if you want**  
   If the site is truly pure static mdBook with no Node dependencies, you can set the build command to just `mdbook build`, point the output directory at `book`, and/or set `SKIP_DEPENDENCY_INSTALL=1`. In that case Yarn never participates. The fact that you needed the 4.18 update implies your Cloudflare build path does involve Node tooling.

**Bottom line**: Yarn is not required by mdBook itself. It is required (or expected) by the Cloudflare build environment whenever Node dependencies are present. Updating to 4.18 aligns your project with the version Cloudflare currently ships by default, so local builds and CI builds stay consistent and you avoid the classic version-skew failures. It is the low-friction path rather than an extra point of failure.
